# AI 研发质量分析工作流 角色提示词设计

> 日期：2026-08-11<br>
> 状态：待书面复核<br>
> 适用仓库：`awesome-qa-prompt`

## 1. 目标

基于 `AI-Quality-Workforce/docs/explorations/AI-研发质量分析流程-MVP.md`，在本仓库新增一套中英文 AI 研发质量分析工作流 Prompt Baseline。

设计必须满足：

- 每个“角色 × 阶段”提供一份独立、可复制使用的 Markdown Prompt；
- 不同角色拥有不同的分析目标、职责边界和输出重点；
- 多角色产物通过独立汇总 Prompt 合并，并保留角色来源、证据和分歧；
- 中文和英文目录、文件、核心行为一一对应；
- 遵守本仓库的输入审计、禁止编造、降级处理和最小可执行原则；
- 不引入 `SKILL.md`、安装脚本或运行时 Prompt 拼装机制。

## 2. 范围

### 2.1 本期范围

- 8 个固定阶段；
- 5 类角色；
- 35 份角色阶段 Prompt；
- 8 份阶段汇总 Prompt；
- 中文 43 份 Prompt，英文镜像 43 份，共 86 份；
- 中英文工作流 README、阶段 README 和仓库入口；
- Prompt 编写标准与静态校验脚本的工作流覆盖。

### 2.2 非本期范围

- Prompt 运行引擎或动态模板拼装；
- 任意循环、并行、条件分支和复杂返工编排；
- 自动执行测试；
- AI 自动完成 Human Task 的通过或驳回；
- 第二期候选阶段和外部平台深度集成。

## 3. 设计选择

采用“独立 Prompt + 统一编写规范”。每份角色 Prompt 都包含完整的角色、输入、任务、约束、降级规则、输出格式和自检，使用时不依赖其他文件。允许必要的通用规则重复，通过统一章节和静态检查降低规则漂移。

不采用公共基础 Prompt 与增量片段拼装，因为这会破坏复制即用，并把组合正确性的责任交给使用者。

## 6. 各阶段角色职责

### 6.1 需求分析

- 产品：业务目标、用户价值、角色、流程、业务规则、范围、验收标准和产品风险；
- QA：可测性、歧义冲突、异常路径、边界条件、测试风险和待澄清项；
- UI/UX：信息架构、任务流、交互状态、反馈、跨端体验和可访问性；
- 技术：技术可行性、系统边界、接口、数据、安全、性能和可观测性风险；
- 汇总：保留来源、共识、冲突和待确认事项，生成需求分析报告。

### 6.2 测试策略

- 产品：业务关键路径、验收重点和业务风险优先级；
- QA：范围、类型、覆盖方法、环境、数据、证据及准入退出建议；
- UI/UX：在高交互、跨端、视觉或无障碍风险出现时提供专项策略；
- 技术：测试层级、接口、集成、技术风险、非功能、可测性和可观测性；
- PM：范围、排期、资源、依赖、里程碑和行动输入；
- 汇总：区分质量事实、策略建议和项目约束，生成测试策略。

### 6.3 测试策略评审

- 产品：业务目标、关键流程和验收范围覆盖；
- QA：完整性、风险覆盖、可执行性、证据和门槛；
- UI/UX：按条件评审体验、跨端和可访问性策略；
- 技术：技术风险、层级、环境、数据、依赖和非功能策略可行性；
- PM：排期、资源、依赖和里程碑可行性；
- 汇总：输出“建议通过 / 建议修订 / 信息不足”，由 Human Task 最终决定。

### 6.4 代码评审

- 产品：按条件检查实现对业务规则、验收标准和用户价值的偏离；
- QA：缺陷风险、回归影响、可测试性、测试缺口和异常处理；
- UI/UX：按条件检查前端实现、交互、视觉、响应式和可访问性；
- 技术：逻辑、架构、接口、数据、安全、性能、兼容性、维护性和可观测性；
- 汇总：合并并去重发现，保留证据位置和角色来源，按严重度输出报告。

### 6.5 测试用例编写

- 产品：按条件补充业务主路径、规则组合和验收场景；
- QA：形成覆盖正向、异常、边界、状态、权限和回归的可执行用例；
- UI/UX：按条件补充交互、视觉状态、跨端、易用性和可访问性用例；
- 技术：补充接口、数据、集成、安全、性能和故障处理用例；
- 汇总：合并、去重、编号并建立需求与风险追踪关系。

### 6.6 测试用例 Review

- 产品：业务规则、验收标准和关键用户旅程覆盖；
- QA：正确性、完整性、可执行性、优先级、重复和遗漏；
- UI/UX：交互状态、体验一致性、跨端和可访问性覆盖；
- 技术：接口、数据、异常、集成和非功能风险覆盖；
- 汇总：列出阻塞问题、补充用例、修改建议和角色来源，供 Human Task 决策。

### 6.7 测试报告

- 产品：按条件检查业务目标、验收范围和用户价值的证据充分性；
- QA：执行覆盖、结果、缺陷、阻塞项、剩余风险和证据完整性；
- UI/UX：按条件检查体验、跨端和可访问性结果；
- 技术：技术缺陷、稳定性、性能、安全、环境和可观测性证据；
- 汇总：生成测试报告；执行报告与缺陷报告同时缺失时只能标记“未执行或证据不足”。

### 6.8 测试报告 Review

- 产品：业务验收证据、未覆盖范围和业务影响；
- QA：结论的证据支持、缺陷和剩余风险完整性；
- UI/UX：体验风险及相关证据是否正确反映；
- 技术：技术风险、环境限制、未验证项和非功能证据；
- PM：行动项、负责人、依赖和时间安排输入；
- 汇总：输出“建议通过 / 建议补充证据 / 建议终止评审”，由 Human Task 最终确认。

## 7. 角色 Prompt 统一结构

1. Prompt 名称；
2. 适用阶段；
3. 角色定位；
4. 参与条件；
5. 允许读取的输入；
6. 输入完整性与版本审计；
7. 本角色分析目标；
8. 分析步骤；
9. 职责边界与禁止事项；
10. 缺失信息处理；
11. Markdown 输出格式；
12. 交付前自检。

角色报告使用以下基础骨架，各阶段按职责增加专属章节：

```markdown
# [阶段]—[角色]分析报告

## 1. 输入审计
## 2. 角色分析摘要
## 3. 已确认事实与依据
## 4. 风险与问题
## 5. 建议与行动
## 6. 与其他角色的协作事项
## 7. 待确认问题
## 8. 置信度与分析限制
```

## 8. 输入、阻塞与降级规则

所有 Prompt 先记录已提供输入及来源版本、缺失的必需输入、缺失的可选输入、当前假设、主要风险和分析限制。

- 必需输入缺失：阻塞，不生成伪完整报告；
- 可选输入缺失：继续执行，说明对完整性、置信度和风险的影响；
- 输入冲突：保留冲突并请求确认，不擅自选择版本；
- 代码评审缺少明确代码版本、Diff 或可读取的仓库内容：阻塞；
- 测试执行报告和缺陷报告同时缺失：测试报告不得给出测试通过结论；
- 所有事实和建议必须追溯到本次输入 Artifact 及版本。

`◇` 角色先输出参与判断：

```markdown
## 参与判断

- 结论：参与 / 不参与 / 信息不足
- 触发条件：
- 判断依据：
- 缺失信息：
- 对阶段产物的影响：
```

“不参与”时结束，不生成空泛分析；“信息不足”时只提出 3—5 个高价值问题。

## 9. 角色边界

- 产品不能虚构技术实现或给出测试通过结论；
- QA 不能擅自修改产品目标和业务验收规则；
- UI/UX 不能把无依据的审美偏好标为阻塞问题；
- 技术不能擅自改变需求范围或把未验证推测写成事实；
- PM 不能修改测试事实、缺陷等级或质量证据；
- 汇总 Prompt 不能通过多数意见删除少数角色的高风险发现。

## 10. 汇总规则

每份汇总 Prompt 必须：

- 保留重要结论的角色来源和输入版本；
- 区分共识、互补意见和冲突意见；
- 合并重复问题时保留原始证据；
- 保留有依据的高风险少数意见；
- 不引入角色报告之外的新事实；
- 只给建议结论，不代替 Human Task 审批；
- 附带摘要、依据、风险、待确认项和追踪信息。

## 11. 文档与校验

实施时同步更新：

- `Workflows/zh/README.md` 和 `Workflows/en/README.md`；
- 仓库中文、英文总入口；
- `PROMPT_AUTHORING_STANDARD.md` 及英文镜像的适用范围；
- `scripts/check-prompts.mjs` 对工作流 Prompt 的规则检查和 README 链接检查。

交付前运行：

```bash
npm run check:all
```

验收标准：

- 中英文各 43 份 Prompt，路径和职责镜像一致；
- 每份角色 Prompt 可单独复制运行；
- 所有参与矩阵槽位都有对应文件；
- 条件角色能正确输出参与判断；
- PM Prompt 不生成或修改质量结论；
- 汇总结果保留来源、证据和冲突；
- 三个评审阶段只输出建议，最终决定留给 Human Task；
- 静态检查与 Markdown 格式检查全部通过。
